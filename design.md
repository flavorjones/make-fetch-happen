# FETCH Design

## Summary

FETCH (Fizzy External Tracker for Card Happenings) is a Rails app that monitors a developer's GitHub notifications for configured repositories and syncs them to a Fizzy board. When a new GitHub artifact (issue, PR, discussion, release) generates a notification, FETCH creates a Fizzy card for it. When subsequent notifications arrive for the same artifact, FETCH adds comments to the existing card.

The first service is GitHub (`bin/fetch-github`). The architecture supports adding other services (GitLab, HackerOne, etc.) as sibling adapters.

## Design Principles

1. **Fizzy cards are the source of truth.** The local database is a fast cache for lookups (e.g., "which Fizzy card corresponds to this GitHub issue?"). If the database is deleted or corrupted, it can be fully regenerated by scanning the Fizzy cards.

2. **Cards store canonical links.** Each Fizzy card created by FETCH contains the GitHub URL so the card-to-artifact mapping can be reconstructed from Fizzy alone.

3. **Incremental by default.** FETCH tracks the latest notification timestamp and only fetches new notifications on subsequent runs. This can be overridden on the command line to re-process all notifications.

## Architecture

Rails app with:

- **ActiveJob workers** that poll GitHub notifications per configured repo
- **ActiveRecord models** for artifact-to-card mappings and sync state
- **A minimal web UI** showing sync status, configured repos, and recent activity
- **CLI entry points** (`bin/fetch-github`) as thin wrappers that trigger jobs or run them inline

## Data Flow

```
1. Job fires (or CLI invoked)
2. Read last_modified timestamp from SyncState (unless --all)
3. GET /repos/{owner}/{repo}/notifications via `gh` CLI
   - Pass If-Modified-Since header for incremental polling
4. For each notification:
   a. Extract artifact type (issue, PR, discussion, release) and canonical GitHub URL
   b. Look up ArtifactCard by github_url
   c. If not found → create Fizzy card (lands in "Maybe?" column), create ArtifactCard record
   d. If found → post comment on existing Fizzy card summarizing the new activity
5. Store the Last-Modified timestamp in SyncState
```

## Models

### ArtifactCard

Maps a GitHub artifact to a Fizzy card.

| Attribute | Type | Description |
|-----------|------|-------------|
| `github_url` | string, unique index | Canonical GitHub URL (e.g., `https://github.com/owner/repo/issues/42`) |
| `fizzy_card_number` | integer | The Fizzy card number |
| `artifact_type` | string | `issue`, `pull_request`, `discussion`, `release` |

### SyncState

Tracks polling state per repo.

| Attribute | Type | Description |
|-----------|------|-------------|
| `repo` | string, unique index | e.g., `sparklemotion/nokogiri` |
| `last_modified` | string | `Last-Modified` header value from the most recent GitHub API response |

## CLI

```
bin/fetch-github --repo sparklemotion/nokogiri --account 6097036 --board BOARD_ID
```

Flags:
- `--repo` — GitHub repo to poll (required)
- `--account` — Fizzy account slug (required)
- `--board` — Fizzy board ID (required)
- `--all` — Ignore saved timestamp, re-process all notifications

## Cache Rebuild

If the database is lost, FETCH can rebuild `ArtifactCard` records by:

1. Listing all cards on the configured Fizzy board
2. Scanning card titles/descriptions for GitHub URLs
3. Recreating `ArtifactCard` records from the discovered links

## GitHub Notifications API

- Endpoint: `GET /repos/{owner}/{repo}/notifications`
- Auth: via `gh` CLI (no token management needed)
- Supports `If-Modified-Since` / `Last-Modified` for incremental polling
- `X-Poll-Interval` header indicates minimum seconds between polls
- Notification `subject.type`: `Issue`, `PullRequest`, `Discussion`, `Release`, etc.
- Notification `subject.url`: GitHub API URL for the artifact

## Web UI

Minimal dashboard showing:
- Configured repos and their sync status (last polled, last modified)
- Recent activity (cards created, comments posted)
- Manual trigger to run a sync
